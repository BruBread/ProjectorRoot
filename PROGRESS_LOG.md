# HY300 Projector Root — Progress Log

Device: Magcubic/HY300-branded projector. **Confirmed Rockchip RK3326** (`rk3326_go`/`rk3326_sgo`), Android 12 Go, `userdebug/release-keys`. NOT Allwinner — despite "HY300" branding being reused across completely different hardware (H713/H726 Allwinner variants exist too; guides for those do not apply here).

## What works reliably (start here)

- **Recovery mode**: hold power button while powering on → boots to standard AOSP Android Recovery menu.
- **Root in recovery**: once in recovery, `adb devices` shows the device; `adb root` restarts adbd as root (`uid=0`, context `u:r:su:s0`) — works every time, no exploit needed. This is unrestricted on this build.
- **Mounting `/data`** (flat ext4 partition): `mount -t ext4 /dev/block/by-name/userdata /mnt_data` — works directly, read-write.
- **Mounting `/system`** (logical partition inside dynamic `super` partition — NOT a flat `by-name/system`): the recovery menu's own "Mount /system" option does **not** work (confirmed via `dmesg` — no device-mapper activity at all, this recovery build's fs_mgr doesn't activate `super`'s logical partitions, and its own `/etc/recovery.fstab` is stale/wrong for this device). Instead, mount it manually via loop device at the exact byte range:
  ```
  losetup -f -s -o 1048576 -S 800915456 /dev/block/by-name/super
  mount -t ext4 -o ro /dev/block/loop0 /mnt_system      # add rw if writing
  ```
  (offset/size found by parsing `super`'s liblp metadata header — see Technical Details below.) **Note:** `losetup`/`mount` auto-detach the loop association on unmount (toybox autoclear behavior) — must recreate the loop device fresh each time before remounting.
- Real `init.rc` used by both recovery and normal boot lives at `/system/etc/init/hw/init.rc` inside that mounted system partition (confirmed via matching line numbers against recovery's own `dmesg` trigger processing).
- USB-drive → file-manager → sideload-install pipeline works in normal boot: copy an APK to a USB flash drive, plug into the projector, open the file manager, tap the APK, allow "install unknown apps" when prompted, install. Confirmed working (installed and ran `Project-Settings` successfully this way).
- Windows-side tooling now installed and working: `rkdevtool` (Tauri/Rust GUI, `C:\Users\user\AppData\Local\rkdevtool\rkdevtool.exe`), Zadig (WinUSB driver binding, via winget), `jadx` (Android decompiler, in project `tools/` folder), Python-based custom AXML manifest parser and DEX string-pool extractor (in project `backups/` folder — `axml_dump.py`, `dex_strings.py`).

## The core problem

Normal Android boot has **no ADB access at all** — `adb devices` shows nothing while sitting on the home screen. The standard "tap Build Number 7 times" Developer Options unlock is confirmed **completely removed from the code** (not just re-gated) — see Attempt 7 below. Every other attempt to get persistent ADB access into normal boot has failed. Recovery-mode root remains the only reliable access we have.

## Attempts tried, in order, with outcomes

**1. Tap Build Number 7x in Settings (manual, via mouse)** — Confirmed does nothing. Mouse input works fine elsewhere in the UI (can navigate normally), so not an input bug. Later confirmed definitively via decompilation (Attempt 7): the click listener was never attached in the OEM's replacement `AboutActivity` — the fields are pure display text.

**2. `/data/local.prop` early-boot override** (`persist.sys.usb.config=mtp,adb`, written from recovery root) — This userdebug-only init feature works for a few seconds after boot (adb briefly visible), but `system_server`'s UsbDeviceManager resets it once it reconciles against `Settings.Global.ADB_ENABLED` (still 0). Tried racing a `settings put global adb_enabled 1` into that ~1-2 second window twice — missed both times, window too short for an external USB round-trip.

**3. Editing `settings_global.xml` directly from recovery** — Blocked. `/data/system` (and `/data/media/0`, i.e. internal storage) are FBE-encrypted (filenames and content garbled when raw-mounted from recovery), unreadable without live decryption keys that only exist inside a booted Android runtime.

**4. Recovery menu's "Mount /system" option** — Confirmed broken (see "What works reliably" above for the manual workaround).

**5. Directly editing `/system/etc/init/hw/init.rc`** (adding a `boot_completed` trigger to force `sys.usb.config=adb`, later upgraded to a self-healing repeating service) — The edit writes fine and is confirmed present right before reboot, but **gets silently reverted by an unidentified boot-time mechanism** every time, confirmed via a marker-file diagnostic (wrote `/cache/hy300_adb_test.txt` from the trigger; never appeared after a full boot). Ruled out as the cause: AVB/vbmeta (already fully disabled on this device — `flags=2`, `algorithm_type=0`, zero descriptors configured, so there is nothing to further disable), and the `backup` partition (`by-name/backup` — completely empty/zeroed, not a restore source). Confirmed the revert does NOT happen live within a recovery session (edit survives an unmount/remount cycle fine) — it specifically happens across an actual boot cycle. **Root cause still unknown.** Likely something Rockchip/OEM-specific outside the named partitions (possibly reserved space before partition 1, invisible to `by-name` symlinks).

**6. Genuine Rockchip Maskrom/loader mode via `adb reboot bootloader`** — Does not reliably reach it. Lands in a non-standard Android-level pseudo-fastboot state (`VID_18D1&PID_D00D`, "USB download gadget", `Class_FF&SubClass_42&Prot_03` — looks like fastboot's class signature but doesn't speak real fastboot protocol). Google's own `fastboot.exe` times out against it even with a correct WinUSB driver bound via Zadig. `rkdevtool` won't touch it either — confirmed by reading its source (`devices.rs`): it only ever matches Rockchip's real vendor ID `0x2207`, never `0x18D1`. The one time genuine `VID_2207&PID_330D` briefly appeared, it was never stably reachable again. **Per community research** (HY300 rk3326_sgo XDA thread), true Maskrom on this exact board needs either opening the case to short a specific PCB resistor/test point, or deliberately erasing the eMMC bootloader (real brick risk if the recovery flash afterward fails — no safety net). User chose not to pursue either, given the risk.

**7. Sideloaded `Project-Settings` app** (github.com/5ham5h33r/Project-Settings — vetted: zero permissions, ~3.4KB plain Java, Defender-clean, APK contents match source) — Installed and ran successfully (proved the sideload pipeline works), but its approach (launch `com.android.tv.settings/com.android.tv.settings.MainSettings` directly by component name) failed with a `SecurityException` — the target activity is not exported. The fallback `Settings.ACTION_SETTINGS` intent just routed back to the same restricted OEM settings app. **Follow-up investigation via decompilation was highly informative:**
   - Pulled and decompiled `TxczSetting.apk` (the actual installed `com.android.tv.settings` package — the OEM built their own complete replacement app under that exact package name, by `com.shzhtxcz.txbox`, runs as `sharedUserId="android.uid.system"`). This is why the direct-component-launch approach failed: there is no `MainSettings` class in this APK at all, only OEM-custom activity names (`MainActivity`, `AboutActivity`, `SystemSettingAppActivity`, etc.).
   - Decompiled `AboutActivity.java` directly: confirmed conclusively that the tap-unlock mechanism is **not hidden or re-gated, it's gone** — the Android/App/Kernel version fields (`stv_android_version`, `stv_app_version`, `stv_kernel_version_code`) have `setLeftBottomString()` calls only, **no `OnClickListener` attached at all**. No number of taps would ever work.
   - `adb_enabled`/`development_settings_enabled` string constants do exist in the compiled app, but tracked down to a single source file: a bundled third-party utility library (`com.blankj.utilcode.util.DeviceUtils`), used only as inert read-only getters (`isAdbEnabled()`, `isDevelopmentSettingsEnabled()`), never called anywhere by the OEM's actual UI code. Dead code, not a real path.
   - Found an exported `BridgeService` with a custom URI scheme (`settings2txcz://`) — a potential integration hook, not yet investigated further.

**8. Self-written "enable developer mode" app** — Not pursued as code, because it's a structural dead end on principle, not just this device: writing `Settings.Global.ADB_ENABLED` requires the `WRITE_SECURE_SETTINGS` permission, which Android never grants to a regular sideloaded/third-party app on **any** Android device (platform-level security boundary, not an OEM restriction). Would hit the exact same `SecurityException` as Attempt 7.

**9. Two web-found rooting guides** — Both turned out to be for a **completely different chip** (Allwinner H713/H726 "HY300 Pro" family: FEL mode, PhoenixSuit, `.fex` firmware format, AllwinnerUSB drivers, `imagewty-tool`). None of it applies to our confirmed Rockchip unit. One did surface a useful, chip-agnostic lead followed up as Attempt 10.

**10. `RKDeviceTest.apk`** (`com.rockchip.devicetest`, Rockchip's own factory diagnostic app, found pre-installed in `/system/app`, runs as `sharedUserId="android.uid.system"`) — Decompiled and traced a complete, real code path: `BootReceiver` listens for `BOOT_COMPLETED`/`MEDIA_MOUNTED` → starts `TestService` → `handleTest()` checks for marker files `Factory_Test.bin`, `Aging_Test.bin`, `SN_Test.bin` (via `ConfigFinder`, checking USB root / SD root / internal storage root) → if `SN_Test.bin` is found, calls `UsbSettings.enableADB(context)` → `Settings.Global.putInt(resolver, "adb_enabled", 1)`, which — running as genuine system UID — should bypass the normal permission check entirely.
   - **Tried twice, both failed**, with no observable effect:
     - Placed `SN_Test.bin` at the root of the USB flash drive (BEARFLASH), plugged into projector while running, waited, unplugged, reconnected PC cable — nothing, no adb, not even a basic USB enumeration change on the Windows side.
     - Tried again with `Aging_Test.bin` (a *visible* test — should play a fullscreen burn-in video if the mechanism fires) placed directly in internal storage root via the file manager, then a full power cycle. **No video played** — straight to the normal home screen.
   - Since even the *visible* Aging Test trigger produced zero observable effect, the whole `RKDeviceTest`-triggering mechanism appears non-functional on this retail build — **most likely because the `com.rockchip.devicetest` package itself is disabled** (a common OEM move: keep factory/service diagnostic tooling on `/system` for warranty purposes, but disable it for retail units so end users can't trigger it accidentally). Not yet confirmed directly (would need to check package enabled-state, which lives in the same FBE-encrypted `/data/system` we can't read from recovery).
   - **Not yet tried**: building a tiny sideloaded app that fires an explicit intent directly at the exported `AgingTestActivity` (bypassing the file-detection/boot-trigger path entirely) — would give a cleaner yes/no on whether the app is alive at all, independent of the `ConfigFinder`/storage-detection layer.

## Technical details worth keeping

**`super` partition liblp metadata** (parsed from the first 16MB, no need to pull the full 2.4GB):
- Geometry: `metadata_max_size=65536`, `metadata_slot_count=2`, `logical_block_size=4096`
- `system` partition extent: **offset `1,048,576` bytes, size `800,915,456` bytes** within `/dev/block/by-name/super`
- Partition layout confirmed non-overlapping, sequential with small alignment gaps: `system` → `system_ext` → `vendor` → `vendor_dlkm` → `odm` → `odm_dlkm` → `product`, total fits within `super`'s actual size (2,516,582,400 bytes)

**`by-name` partition symlinks present on this device** (Rockchip standard, non-A/B): `backup`, `baseparameter`, `boot`, `cache`, `cust`, `dtbo`, `logo`, `metadata`, `misc`, `mmcblk2`, `mmcblk2boot0/1`, `recovery`, `security`, `super`, `trust`, `uboot`, `userdata`, `vbmeta`. Notably **no flat `system` symlink** (it's inside `super`) and **no `vendor_boot`** (despite recovery's fstab template referencing one — that fstab is stale/generic, not accurate for this build).

**`boot.img` header** (parsed directly, header_version=2): kernel cmdline includes `androidboot.selinux=permissive` and `buildvariant=userdebug` — SELinux is permissive system-wide. Boot ramdisk contains **no `init.rc`** — this device uses modern system-as-root two-stage init (first-stage does compiled-in fstab-driven mounting only, then switch_root into `/system`), so there was never anything to patch in the boot ramdisk itself.

**`vbmeta`**: `magic=AVB0`, `flags=2` (verification already disabled), `algorithm_type=0` (unsigned, no hash/signature configured), all descriptor offsets/sizes are zero. AVB was never actually enforcing anything on this device — ruled out as a cause of anything.

**System app inventory** (`/system/app` + `/system/priv-app`, from the read-only mount): no overtly malware-named packages found in this pass (unlike a sibling Allwinner-chip device where specific spyware packages were documented by the community — `com.hotack.silentsdk`, `com.hotack.writesn`, etc. — those are confirmed on different hardware, not this unit). Notable OEM app family: `TxczSetting`, `txcz_app`, `txcz_launcher`, `txcz_ota`, `txczbox`, `txcztest` (all `com.shzhtxcz.txbox.*` / `com.android.tv.settings` per the actual package name) — likely worth a closer look at `txcz_ota` given the unexplained revert mechanism in Attempt 5, and `txcz_launcher` since it's presumably what hides things from the home screen. Not yet investigated.

## Attempt 11: deep research into the Attempt-5 init.rc revert mechanism (2026-09-16)

I researched each candidate mechanism against the exact observed symptoms (write succeeds and survives unmount/remount within a recovery session; only an actual power-cycle reboot reverts it; a `/cache` marker file added via the same init.rc edit never appears either; AVB/vbmeta already fully disabled; non-A/B device but `super`'s liblp metadata reports `metadata_slot_count=2`). Full per-item JSON (how_it_works, evidence fit, exact test/bypass commands, citations) saved in `analysis/init_rc_revert/`.

Ranked outcome:

1. **AOSP overlayfs remount shadowing (`fs_mgr_overlayfs`) — High likelihood.** Generic, documented AOSP mechanism (`system/core/fs_mgr/README.overlayfs.md`, `init/first_stage_mount.cpp`). First-stage init assembles an overlay over `/system` right after `switch_root`, *before* second-stage init ever parses `init.rc` — matches "reverts before/during early init" exactly, and explains why Recovery (different fstab, doesn't run this logic) never sees the problem. Non-A/B default backing store is `/cache/overlay/`, or a `scratch` logical partition inside `super` if there's no physical `/cache` — NOT `/data/overlay` (a wrong assumption we'd have made otherwise). Test: check for a `scratch` by-name/logical partition and `/cache/overlay/` presence via `lpdump`; a full round-trip canary test would require ADB access during normal boot, which we don't have yet.
2. **Wrong losetup offset/slot — Medium likelihood.** Our manual mount uses a hand-computed offset/size (1,048,576 / 800,915,456) against `super`. The device reports `metadata_slot_count=2` despite being non-A/B, and AOSP dynamic-partitions allow a logical partition to span multiple non-contiguous extents. If our offset only covers one extent or the wrong metadata slot, edits land in a self-consistent but boot-irrelevant region — a "perfect" silent revert with no exotic logic needed. Test: `lpdump` both metadata slots, list every extent for `system`, and diff against what we're currently mounting.
3. **TXCZ OEM watchdog/`txcz_ota` — Low-medium.** No public documentation on this vendor exists anywhere. The `/cache` marker's total absence argues *against* an app-level (BOOT_COMPLETED-triggered) restore, since no APK can run before init.rc is parsed — but a native pre-init binary tied to the TXCZ toolchain isn't ruled out without decompiling `txcz_ota` (still on the open-threads list below).
4. **fstab-level dm-verity (independent of AVB) — Low.** Real, documented, and fits the boot-only timing, but dm-verity can only produce an I/O error / restart / panic / passthrough-with-log-warning on a hash mismatch — it has no mechanism to silently substitute old good content while continuing to boot cleanly. Doesn't match the observed behavior.
4. **Reserved pre-GPT eMMC region (idblock/loader1/loader2/trust.img/U-Boot ENV) — Low.** These regions are real and documented for Rockchip, and the timing (only re-executes on a genuine cold boot) fits unusually well, but zero precedent exists anywhere of this class of region restoring `/system` files at boot.
- **`recovery-from-boot.p` — Ruled out.** Purely a `/boot` → `/recovery` one-way refresh mechanism (`flash_recovery` service, `install-recovery.sh`/`applypatch`). Has no code path that ever touches `/system` or `init.rc`.

**Immediate next diagnostic (cheap, fully read-only, no reboot needed):** from Recovery root, `lpdump` `super`'s metadata for both slots, list every extent for the `system` partition, and cross-check against our hand-computed offset — this single check discriminates between the #1 and #2 leads, which together account for most of the probability mass.

## Attempt 13: live on-device testing conclusively rules out every Android-side hypothesis (2026-09-16)

Projector back in hand. Ran the Phase-1 checklist from the plan, then extended it once results demanded it.

- **Canary round-trip:** planted a unique string in `/system/etc/init/hw/init.rc` (plus the boot_completed trigger + `/cache` marker from Attempt 5), `sync`'d, cleanly unmounted, real power-cycle reboot to normal Android home screen, then back into Recovery to re-check the *raw* loop-mounted partition (bypassing any OS-level view). Result: canary completely gone, file back to the exact pristine 6023-byte content (md5-verified identical to `backups/init_rc_orig.rc`), mtime back to the AOSP reproducible-build `1970-01-01 00:00:00` (our edit had a real 2026 timestamp), and the inode number changed *again* (10839 orig → 11220 our edit → 2287 after reboot) — a fresh file write, not a live in-place scrub. **This kills the overlayfs hypothesis outright**: overlayfs never touches the lower/raw partition, so the raw bytes should have stayed edited if that were the cause. `/cache/hy300_adb_test.txt` marker never appeared (confirms the revert happens before init.rc is ever parsed) and there is no `overlay` directory anywhere under `/cache` (further independent confirmation against overlayfs).
- **Reserved pre-GPT region (idblock/loader1/Vendor-Storage/ENV/loader2, first 4MB before the GPT):** dumped before and after the reboot — byte-identical (nothing wrote to it), and contains no `init.rc`-shaped plaintext content anywhere (82% zero bytes). Rules out a plaintext golden copy stored there.
- **`backup` partition properly checked this time:** it's actually 372MB, not the 4MB previously assumed — sampled 14 offsets across its full span, all identical to an all-zero 1MB block. Genuinely empty end to end.
- **Round 2 test — does the revert wipe *anything* or just init.rc?** Edited `/system/etc/hosts` (confirmed via a failed `cp` that this file did *not* exist in the pristine build — so this is effectively a brand-new file) and re-planted the init.rc canary. After another real reboot: `/system/etc/hosts` is gone entirely (not reverted-with-old-content — genuinely absent), and init.rc is back to pristine again (new inode: 10916). **This is a whole-`/system`-repopulation-from-reference, not a targeted watcher on init.rc specifically.**
- **Round 3 test — is this normal-boot-specific?** Re-planted both canaries, this time rebooted **straight back into Recovery** (held power immediately, never let it reach the normal home screen). Both canaries were wiped anyway. **This is the decisive result: Recovery and normal boot use completely different boot images/ramdisks and share zero Android-side code path.** The only thing that runs before *both* is U-Boot (or the BootROM/miniloader/trust stage before it). This rules out every remaining Android-side hypothesis (including `txcz_ota`/any installed app, already weak given the marker-timing evidence, and any first/second-stage init logic specific to normal boot).
- **Checked for a bootloader-level culprit, offline-safe (no writes):** pulled and string-scanned `uboot` (4MB) and `trust` (4MB) partitions. `uboot` contains 4 "txcz" hits — all just a cosmetic build-tag (`U-Boot 2017.09-g2807ac1 #txcz`), confirming TXCZ forked/rebuilt U-Boot themselves but no plaintext restore logic or embedded init.rc content found. `uboot.bin`'s compiled-in default environment shows `bootcmd=boot_android ${devtype} ${devnum};boot_fit;bootrkp;run distro_bootcmd;` — `boot_android` is Rockchip's native, compiled-in Android boot-select command (ARM machine code, not a readable text script), so any custom TXCZ restore logic living inside it can't be found via plaintext string search. Also string-scanned the full `boot` partition (kernel + ramdisk) and the compiled `/init` binary from the ramdisk — both come back stock AOSP/Linux, no vendor restore logic, just the same `txcz` build-tag noise.

**Conclusion:** the revert is caused by something in U-Boot (or earlier) that unconditionally repopulates `/system` (at least `init.rc`, and apparently arbitrary other content) from a reference on every cold boot, regardless of boot target. The actual mechanism/reference location has not been located — everything checked so far is either stock or shows no plaintext evidence, but plaintext string search would miss a compressed/packed reference. Following up with a desktop-only research pass (`uboot_anti_tamper_research/`, see plan) before considering any device-touching next step, since defeating this for real likely means reflashing `uboot`/`trust` — real brick risk, Maskrom-only recovery, already declined once.

## Attempt 14: desktop-only research pass on the U-Boot-level mechanism (2026-09-16)

Desktop-only, zero device interaction; full detail in `analysis/uboot_research/*.json`.

- **Provenance — confirmed bespoke, not stock.** Read Rockchip's actual public U-Boot source (`rockchip-linux/u-boot`, `cmd/boot_android.c` / `common/android_bootloader.c`). `boot_android` originates from an upstream (AOSP-licensed) 2017 patch series adding Android boot flow to mainline U-Boot; Rockchip's fork carries it forward with only `rk_avb_*` AVB hooks added. Stock flow: BCB read → slot/mode select → load image → AVB check → on failure, retry a slot (never rewrites a partition). Given this device is non-A/B and its `uboot.bin` carries a distinct `#txcz` build tag, **the whole-partition-repopulation behavior we observed cannot be stock — it's a bespoke TXCZ patch** to their own private fork. The exact commit tag (`g2807ac1`) doesn't appear in any public Rockchip repo.
- **Compressed-reference re-scan — closes the "hiding in a file we already have" door.** Re-scanned every local dump (uboot.bin, trust.bin, boot_orig.img, ramdisk, `/init` binary, super_header.bin) for compression/archive magic bytes, not just plaintext. Found real compressed streams, but every single one is a benign, fully-explained toolchain artifact: a `CONFIG_IKHEADERS` kernel-header tarball inside `boot_orig.img`, and multiple `.gnu_debugdata` MiniDebugInfo sections (standard `strip`/`objcopy` output embedding a compressed mini-symbol-table in a stripped binary) inside `init_extracted.bin` and `super_header.bin`. No packed `/system` image or `init.rc` copy anywhere in any of the 7 files checked.
- **Disassembly — blocked on missing tooling, but corrected our model.** No objdump/radare2/Ghidra/IDA installed on this machine; nothing was installed without asking first, so no real instruction-level trace of `boot_android` happened. Raw byte inspection did correct an assumption: `uboot.bin` is **AArch64** (not ARM32 as assumed), Rockchip `LOADER` header, real code starts at file offset `0x800`. The 4MB file is just two redundant copies of the same image (`loader1`/`loader2`, standard Rockchip layout), not a hidden second payload. Function-name strings near the `boot_android` cluster are all stock Rockchip/AOSP helper names (`android_image_load_by_partname`, `gpt_restore`, `fb_mmc_flash_write`) — nothing bespoke-looking survived to the string level, consistent with the custom logic being compiled code with no distinctive strings, or living in a spot not yet examined. No `ext4write` string anywhere (only `ext4load` ×4) — weak evidence against an ext4-file-API-level restore, doesn't rule out a raw block-level overwrite. **New unexplored lead:** a quick pass over `trust.bin` turned up `system` (4×) and `restore` (8×) string hits, flagged but not investigated (out of scope for that item).
- **Prior art — no direct hit, two analogous mechanism classes.** No public report of TXCZ/`rk3326_sgo` with this exact symptom (TXCZ only shows up in plain firmware-request threads on XDA). Closest historical analog: HTC T-Mobile G2/Desire Z's 2010 NAND-lock (`@secuflag` in radio NVRAM triggers bootloader-level write-protection on system/boot/recovery) — **defeated entirely in software** via the "gfree" exploit (power-cycled the eMMC to clear the flag, no bootloader reflash). Second class: eMMC-spec Power-On Write Protection applied at bootloader stage, patented for cheap Chinese STBs (CN105069381A) but confirmed on MediaTek, not Rockchip. Neither is confirmed to apply here — analogy only.

**Where this leaves things:** mechanism confirmed to be a bespoke TXCZ addition living in U-Boot or earlier, not stock Rockchip. Exact logic and reference-data location still unlocated. Real progress from here needs either (a) installing a disassembler (`pip install capstone` is the lightest option) to actually trace `boot_android`'s compiled logic starting at the corrected AArch64/offset-0x800 basis, or (b) accepting this as a deliberate, low-level anti-tamper design. Defeating it for real would mean patching and reflashing `uboot`/`trust` — genuine brick risk, Maskrom-only recovery, already declined. Note the HTC precedent above is a reminder that a software-only defeat (no reflash) has historically been possible for this *class* of mechanism, even if this specific device's variant is still unknown.

## Attempt 15: real disassembly of uboot.bin, partial trace of do_boot_android (2026-09-16)

Installed `capstone` (Python AArch64 disassembler, desktop-only, zero device interaction) and ran a real disassembly pass, since the prior byte/string-only pass couldn't trace actual code.

- **Load base resolved with high confidence: `0x200000`** (virtual_address = 0x200000 + (file_offset − 0x800)). Found by cross-validating two independent literal pointers in the `boot_android` command's `cmd_tbl_s` struct (name string pointer + usage string pointer, at the exact struct-field spacing AArch64 U-Boot's `cmd_tbl` layout predicts) — not a guess, both pointers independently resolve to the correct string offsets under this one base.
- **`do_boot_android` located: file offset `0x8f74`** (entry) / `0x8f88` (main body). Confirmed by the function's own argument-count validation logic matching the command's documented usage string exactly (independent second confirmation beyond the pointer match).
- **Partial trace, ran out of budget before reaching a write:** `do_boot_android` is a thin wrapper. It calls a short helper (~0x9b72c, likely a string-copy/slot-id utility, not confirmed), reserves a DRAM region via Rockchip's "Bidram" subsystem (normal legitimate behavior for loading a boot image), then calls into what looks like the real Android-boot-flow function at file offset `0x2a0a0`, which dispatches via a switch/jump-table on a boot-image-header field (consistent with **header parsing**, not a partition write). Did not reach any raw MMC/eMMC block-write instruction, LBA constant near sector 2048 (`system`'s start), or hash/checksum-against-fixed-value comparison. The two candidate write-related symbols (`blk_dwrite`, `fb_mmc_flash_write`) weren't resolved to call sites within this pass's heuristics (known false-negative-prone method, not a ruled-out result).
- **`trust.bin`'s earlier "system"/"restore" string hits are a confirmed dead end** — checked and they're all benign OP-TEE OS internals (`system.pta` pseudo-TA name, VFP register save/restore routines, a memory-mapping error string), nothing related to Android's `/system` partition.
- **Honest limitation:** reaching an actual write/hash instruction would need either several more hours of manual ADRP/branch tracing, or loading the binary into Ghidra/IDA with the now-confirmed image base (`0x1FF800`, i.e. `0x200000 − 0x800`) for proper interactive cross-reference navigation — a heavier tool install than capstone, not yet done.
- Reusable artifacts saved (no need to redecode from scratch next time): `init_rc_revert/emmc_dumps/scratch/insns.pkl` (full linear disassembly of the first image copy) and `targets2.pkl` (ADRP+ADD/LDR cross-reference map, has known false-positive/negative caveats).

## Attempt 16: Ghidra-based full trace of do_boot_android — confirmed dead end, pivots to bootrkp (2026-09-16)

Installed Ghidra 12.1.3 (official NationalSecurityAgency/ghidra GitHub release, sha256-verified against GitHub's own published digest — no unofficial mirror) plus the machine's existing Oracle JDK 21, desktop-only. Imported `uboot.bin` as raw AArch64 at the previously-confirmed base (file offset 0 → VA `0x1FF800`), ran full auto-analysis, and walked `do_boot_android`'s complete call graph (~20 functions, 2-3 levels deep).

**Result: `boot_android` is a dead end — confirmed moderate-to-high confidence.** Its entire normal flow is device lookup → find `misc` partition → read BCB → decide boot mode → **read** (not write) the `boot`/`recovery` partition into RAM via `android_image_load_by_partname`, plus a DTBO overlay **read**. Resolved the actual addresses of all 7 previously-suspected "smoking gun" functions (`fb_mmc_flash_write`, `gpt_restore`, `write_mbr_and_gpt_partitions`, `android_bcb_write`, `gpt_verify_headers`, `is_valid_gpt_buf`, `set_protective_mbr`) via Ghidra's string cross-references — **none of them are called anywhere in `do_boot_android`'s call graph.** They belong to `fastboot flash`/the `gpt` command/BCB-write-on-explicit-reboot-command — all operator-triggered, not something that fires unconditionally on every boot. (Two callees weren't fully expanded — the final kernel-boot step and the interactive fastboot loop — structurally very unlikely to hide a write given their jobs, not 100% ruled out.)

**New, more promising target identified:** recall `bootcmd=boot_android ${devtype} ${devnum};boot_fit;bootrkp;run distro_bootcmd;` — since `boot_android` is clean, the next two commands that actually run on every boot are `boot_fit` and **`bootrkp`** ("boot RK partition" — a Rockchip-specific custom command, not part of the stock Android boot flow at all). Neither has been traced yet: both strings exist in rodata but have zero incidental code cross-references (unlike `boot_android`, which got lucky with error-string references from neighboring functions), so Ghidra's auto-analysis never found their handler code from string xrefs alone. Next step (already identified, in progress): locate U-Boot's command table directly via structural pattern-matching (a run of `{name_ptr, maxargs, repeatable, handler_ptr, usage_ptr, help_ptr}`-shaped structs, ~48-56 bytes each) to get `do_boot_fit`/`do_bootrkp`'s real addresses directly, bypassing the string-xref limitation entirely.

## Attempt 17: structural cmd_tbl scan finds bootrkp (and proves boot_fit doesn't exist), full trace confirms bootrkp is also a dead end (2026-09-16)

Desktop-only, no device interaction. Wrote a standalone Python scanner (`init_rc_revert/emmc_dumps/scratch/find_cmdtbl.py`, `walk_cmdtbl.py`) instead of relying on Ghidra's string-xref search: used the already-confirmed `boot_android` cmd_tbl entry (file offset `0xdb928`) as an anchor, located the exact struct layout by cross-correlating the pointer-to-"boot_android"-string with the pointer-to-`do_boot_android` nearby, and derived the real `cmd_tbl_s` struct for this build: **48 bytes** — `name_ptr(8) | maxargs(4)+repeatable(4) | cmd_ptr(8) | usage_ptr(8) | help_ptr(8) | complete_ptr(8)`. Walked the table at that fixed 48-byte stride both directions from the anchor until entries stopped validating (name resolves to a real string + cmd resolves to 4-aligned code) — this recovered the **entire alphabetical command table intact**, 64 commands from `android_print_hdr` to `pxe`, file offsets `0xdb7d8`–`0xdc3a8`.

**Two concrete results:**
1. **`boot_fit` does not exist as a compiled U-Boot command in this binary at all.** The table is alphabetically packed with zero gap between `boot_android` (`0xdb928`) and the very next entry `bootavb` (`0xdb958`, exactly one 48-byte stride later) — `boot_fit` would sort exactly between them alphabetically, and there is no room for it. This is a structural proof, not a heuristic: whatever `bootcmd` string is quoted in older notes, `boot_fit` on this device either isn't a real subcommand (hush prints "Unknown command" and moves on) or that recollection of `bootcmd` is simply wrong for this build. Either way it's provably not where any anti-tamper logic lives.
2. **`do_bootrkp` located at VA `0x208ab0`** (file offset `0x9092b0`... i.e. `0x0092b0`), entry #14 in the table, `usage="Boot Linux Image from rockchip image type"`.

**Full Ghidra decompile + 5-level call-graph walk of `do_bootrkp`** (script: `tools/ghidra_scripts/TraceBootrkp.java`, full output: `init_rc_revert/emmc_dumps/scratch/bootrkp_trace_full.log`, ~130 functions visited): **confirmed dead end, same shape as `boot_android`.** Its logic: look up `misc` partition → call a routine that reads a **factory attestation key blob** (magic `"CA\0"`, private key + certificate chain) from a reserved region at the *end* of the `misc` partition and loads it into TEE-backed secure key storage (Android Keymaster/attestation provisioning — a real Rockchip feature, unrelated to `/system`) → read OEM-unlock status into a boot arg → decide `boot` vs `recovery` target (same BCB-driven logic as `boot_android`) → look up and **read** (not write) the `kernel`/`ramdisk`/`fdt` partitions into RAM → validate the FDT header → hand off to the `booti` command to actually boot. Every partition touched (`misc`, `boot`/`recovery`, `kernel`) is opened for **read only**. Cross-checked against all 7 previously-identified smoking-gun addresses (`fb_mmc_flash_write`, `gpt_restore`, `write_mbr_and_gpt_partitions`, `android_bcb_write`, `gpt_verify_headers`, `is_valid_gpt_buf`, `set_protective_mbr`) — **none reached anywhere in the call graph.** No `system`/`super` partition string is even referenced in this function or its callees.

**Where this leaves things:** both commands that unconditionally run every boot (`boot_android`, `bootrkp`) are now fully traced and are dead ends — read-only boot-image loaders, no partition-restore logic anywhere in either. `boot_fit` is proven not to exist as compiled code. The only unexamined piece of the original `bootcmd=boot_android ${devtype} ${devnum};boot_fit;bootrkp;run distro_bootcmd;` chain is **`run distro_bootcmd`** (the generic Das U-Boot distro-boot script, which on most Rockchip boards just tries USB/network/whatever media in sequence — low a priori likelihood of containing bespoke restore logic, but not yet checked). Reusable artifacts for a follow-up session: `find_cmdtbl.py`/`walk_cmdtbl.py` (recover the full command table from any similar dump instantly, no Ghidra needed), `TraceBootrkp.java` (Ghidra headless call-graph walker, reusable pattern for tracing any other command), and the existing `ubootproj` Ghidra project (already fully auto-analyzed, no need to re-import).

## Attempt 19: cross-build comparison closes off uboot.bin entirely, new logical finding (2026-09-16)

Compared `do_boot_android`/`do_bootrkp` between the two firmware builds (Jun 2025 stock ROM vs. our Jan 2026 device) using the existing command-table-recovery method, re-anchored independently in each binary.

- **Both functions sit at identical file offsets in both builds** (`do_boot_android` fo `0x8f74`, `do_bootrkp` fo `0x92b0`) — not a coincidence, independently re-derived in each binary via the command table walk.
- **Instruction-for-instruction identical in both builds.** `do_boot_android` (62 instructions) and `do_bootrkp` (166 instructions): zero mnemonic differences between the two builds. Every raw byte difference is just ADRP/ADD/BL operand drift from unrelated relocations elsewhere in the 7-months-newer binary — confirmed by checking that the actual call targets are themselves byte-identical function bodies, just at different addresses. **These two functions have not changed at all between June 2025 and January 2026.**
- **New logical finding, not previously stated explicitly:** `do_boot_android` calls into the loaded kernel and never returns on success. Since the device is known to boot Android successfully every time (the whole premise of this investigation — it boots fine, only `/system` content reverts), `boot_android` must be succeeding on every normal boot, which means **`boot_fit`, `bootrkp`, and `run distro_bootcmd` never execute at all** in the chain `bootcmd=boot_android ${devtype} ${devnum};boot_fit;bootrkp;run distro_bootcmd;`. The entire back half of that chain is dead code for this scenario, in both builds. (Flagged as inference from known U-Boot semantics + observed boot behavior, not a directly-traced non-return path — but a solid inference.)

**Where this leaves things:** `uboot.bin` is now exhausted as a suspect across two independent firmware revisions, and `trust.bin` was already confirmed byte-identical between builds with no relevant references. The mechanism is not in either file. Remaining candidates: (a) the **pre-GPT reserved region** (idbloader/TPL+SPL, the BootROM-loaded first stage that runs *before* U-Boot proper and before the GPT/partition table is even read) — already dumped (`init_rc_revert/emmc_dumps/pre_gpt_pre_reboot.bin`/`pre_gpt_post_reboot.bin`) and string-searched (clean, no plaintext content), but **never disassembled as code** — this is the most promising unexamined region given it runs earlier than everything already ruled out; (b) `trust.bin`'s actual runtime TEE behavior (only string-scanned so far, not behaviorally traced); (c) reopening Android-side possibilities, though this is weaker given the recovery-vs-normal-boot test already ruled out everything Android-side once.
